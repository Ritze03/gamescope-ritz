# Terminology

Project-specific vocabulary. When the user uses a term defined here, use the same
meaning.

**If the user uses a non-standard term that is not defined here, ask what they mean by
it before acting on it.** Once its meaning is clear, add it to this file. Keep this
file up to date automatically: whenever the user introduces or clarifies a term, add or
amend the entry here.

## Terms

- **steamcompmgr** — the X11 window-manager subsystem inside gamescope (historically a standalone project this compositor absorbed); not the whole binary.
- **Backend** — the display-output abstraction (`IBackend`); one of DRM, SDL, OpenVR, Headless, Wayland, selected at startup. Not a "client backend".
- **Nested mode** — running gamescope as a window inside an existing desktop session (SDL/Wayland backend).
- **Nested window** — a client window running *inside* gamescope's own embedded Xwayland session (an app or game window, addressed by `xwayland_ctx_t`/`steamcompmgr_win_t`) — not gamescope's own outer window, which **Nested mode** (above) is about. The General area's "Force maximize nested window" toggle (`display.force_windows_fullscreen`, mirrors `--force-windows-fullscreen`) names this sense: it makes every such window open at the full nested canvas size regardless of its own requested size. See `superdoc/features/resolution-and-refresh.md`'s "Force maximize nested window" section.
- **Embedded mode** — gamescope owning the physical display directly via DRM/KMS (the Steam Deck / console usecase).
- **Override window** — a window painted on top of the focused app window (e.g. the Steam overlay) without taking full focus.
- **Underlay window** — a window painted beneath the current override, preserved across override changes.
- **Look** — a `gamescope_control` protocol concept (`set_look`/`unset_look`) applying a display colour/visual profile.
- **FrameInfo_t** — the per-composite-pass description of every layer (windows, cursors, overrides) to be composited in one Vulkan pass.
- **Connector** — an `IBackendConnector`: an output port/display (a DRM connector, or a VR overlay "connector" under the OpenVR backend).
- **VirtualConnectorKey_t** — the key used to look up per-output focus state in `g_VirtualConnectorFocuses`; supports multi-display and multi-VR-overlay setups.
- **ConVar / ConCommand** — gamescope's runtime tunable-variable and debug-command system (`src/convar.h`), settable live from the script console.
- **EASU / RCAS** — the two FSR1 shader passes: edge-adaptive spatial upscale, and robust contrast-adaptive sharpen.
- **NIS** — NVIDIA Image Scaling, an alternative upscaling filter to FSR.
- **PQ (Perceptual Quantizer)** — the HDR10 EOTF gamescope converts to and from nits (`pq_to_nits` / `nits_to_pq`).
- **Xwayland ctx** — `xwayland_ctx_t`, one per spawned Xwayland server instance (gamescope can run several; `--xwayland-count`).
- **Reshade effect** — a post-process shader effect applied via the ReShade-compatible pipeline; distinct from the FSR/NIS *scaling* filters.
- **gamescope_control** — the primary custom Wayland protocol interface external tools (Steam, `gamescopectl`) use to query and drive gamescope.
- **WSI layer (FROG)** — `VkLayer_FROG_gamescope_wsi`, the Vulkan layer games load so their swapchain is redirected into gamescope's compositing pipeline.
- **mangoapp** — gamescope's integration point for the MangoHud-style performance overlay (`src/mangoapp.cpp`).
- **Command palette** — the searchable, ranked index over every registered Entry and Parameter (`src/Overlay/UI/CommandPalette.{h,cpp}`, drawn from `Shell.cpp`). Search with an empty query is browsing; there is no second "list everything" path.
- **Launcher** — the command palette drawn **alone over the game**, with no shell behind it (`Left Ctrl + Right Shift` while the overlay is closed — rebound from `Left Ctrl + Right Ctrl` 2026-09-01, see CHANGELOG.md). The user's *"Launcher Style UI"*. Distinct from the palette drawn *over an open shell*, which is the same widget with a scrim and a different Esc. Direction B's contribution, kept as a feature rather than as the whole GUI — see AUTONOMOUS-DECISIONS D25. The binding is a **toggle**: pressed again while the palette is already up, it closes what it opened rather than opening something else — `SetVisible(false)` if the launcher is alone on screen, `RequestClosePalette()` (leaving the shell untouched) if the palette is layered over a shell that was opened separately. See IMPLEMENTATION.md's Issue #88 entry.
- **Launcher-UI** — the user's own name for the **Launcher** (see that entry above); use interchangeably with it.
- **Shell** — the E2 settings overlay proper: slab, rail, sheet and inspector (`src/Overlay/UI/Shell.cpp`). "The full/clickable overlay" in the user's wording. The launcher is deliberately *not* part of it. Closed with the X in the title bar; there is no separate settings tab for this any more (the former `setup.shell` tab was removed 2026-08-27).
- **Click-UI** — the user's own name for the **Shell** (see that entry above); use interchangeably with it.
- **HUD** — the on-screen readout drawn over the game: a single FPS integer (`src/Overlay/FpsDisplay.cpp`'s `DrawReadout()`), positioned by a 9-point anchor plus pixel margins. Its settings-panel area is `system.hud` ("HUD" in the rail), renamed from `system.monitor`/"Monitor" (HUD layouts Phase 1, 2026-09-02) because "Monitor" read as ambiguous against this project's own "Overlay" naming, which **Shell**/**Click-UI** above already claims. Distinct from both the **Shell** (the settings surface that hosts the HUD's own settings tab) and the **Launcher** (an unrelated command-palette feature). Used to carry a small **profiler** (see that entry below) and a named per-module layout system; both were removed 2026-09-03 as a deliberate scope reduction, and the current minimal `system.hud` area (Show HUD / anchor / margins / font size) is a placeholder a later phase rebuilds properly.
- **Adaptive Gamma** — the Shaders effect added 2026-09-08 (`image.shaders.adaptive_gamma`, `src/shaders/effects_curve.h`'s `ag_*` block), from the user's *"Make something similar, but make it gamma based"*. It reuses **Adaptive Brightness**'s measured statistics but its whole operator is one exponent — `x^g` with `g` chosen to land the smoothed median on Target — so it adjusts *contrast* and cannot clip, where Adaptive Brightness's levels gain adjusts *exposure* and needs a shoulder to stop it blowing out. **Mutually exclusive with Adaptive Brightness**: turning either on turns the other off, because both aim the same mid-tones at the same target from the same pre-effect statistics. Its bounds are the user-facing **Max lift** and **Max darken** params, not constants. Since 2026-09-09 it also has its **own** adaptation speeds (**Adapt to brighter** / **Adapt to darker**): before that the shared measure pass smoothed its statistics at Adaptive Brightness's speeds, i.e. at sliders unreachable while this effect was the one running. Since 2026-09-14 it also shares **Leave dark scenes alone** with Adaptive Brightness, but the two keep independent copies, not one shared row (schema 4→5, commit 8660451): a briefly-shared `reshade.dark_floor` key (schema 4) split into `reshade.adaptive_gamma.dark_floor` — this row's own eighth `Param` — and `reshade.adaptive_brightness.dark_floor`, a standalone row placed under Adaptive Brightness's switch (GUI id `image.shaders.adaptive_brightness_dark_floor`) rather than a ninth `Param`, because that row was already at the 8-`Param` budget with none spare; `ConfigManager.cpp`'s `Migrate_4_to_5()` copied the old key's value into both. Each fades its own effect's exponent/gain back to the untouched picture once the smoothed scene is darker than its own floor — without it, a near-black scene drove either effect's exponent/gain to its user-set ceiling regardless of the pixel, which the user reported as the picture being "destroyed"/binarised rather than merely lifted. See `superdoc/features/shader-effects.md`.
- **Adaptive Brightness V2** (`image.shaders.adaptive_brightness_v2`, added 2026-09-14;
  the GUI title's capitalization was corrected to this, matching every other effect's
  sentence case, the same day) —
  a THIRD choice alongside **Adaptive Brightness** and **Adaptive Gamma** above, not a
  replacement for either: the user's own instruction was *"Call it 'Adaptive brightness
  V2' in the GUI. Implement it fully ... DO NOT REMOVE THE ORIGINAL!"*. Its curve is a
  **toe-gamma** — `x^g` far from black but bending into a straight line of slope `S`
  (the user's own **Max lift**) at black — so the largest amplification anywhere in the
  frame is `S` by construction; every effect above lifts with a plain `x^g`, which has an
  *infinite* slope at black and structurally binarises a near-black scene (see
  `superdoc/planning/adaptive-brightness-v2-plan.md`'s §3.2). A **Shape** row offers a
  second curve, **Knee**, that leaves highlights exactly untouched instead of compressing
  them a little everywhere. Its `g` comes from a **content anchor** — a rank-window mean
  over frame taps *above* a black floor, so the median of the void (unlit map geometry)
  cannot dominate the median of the content (floors, players, lights) — deepened, in
  **Scene** adaptation, toward a **Target brightness**, with a **scene-cut** detector
  that snaps the anchor instead of sliding across a flash or a door. **Stage 2** (a fast
  guided filter on luma, quarter resolution) splits the picture into base and detail so a
  lifted region keeps its own texture/outline contrast (**Detail**) instead of the flat
  wash a global curve leaves. **Stage 3** (added the same day) adds **Clarity**: a SECOND,
  finer guided-filter pair (radius `r/4`) whose difference from the Stage-2 base is the
  4..16px "silhouette band" — a limb or weapon outline's own scale — added into the
  detail term with its own gain; a hard, already-visible edge has `a ≈ 1` in *both*
  filters, so the band is `≈ 0` there and nothing rims. Mutually exclusive with **both**
  Adaptive Brightness and Adaptive Gamma (turning any one of the three on turns the other
  two off) — all three aim the same mid-tones at the same target from the same
  pre-effect statistics. **Darkening** (added 2026-09-14, the user: *"Make it able to
  make the image darker (both full and on parts of the image)"*) makes the curve
  two-sided — the SAME family, convex instead of concave above a pivot at Target
  brightness (**Max darken**/**Darken**, the mirror of **Max lift**/**Lift**) — so a
  bright region darkens while a dark region lifts in one frame; `kParamBudget` went
  8 → 10 for its two new params. See `superdoc/features/shader-effects.md`'s own section
  for the formulas and measurements.
- **About** — the settings overlay's `system.changelog` area, labelled "Changelog" until 2026-09-09 and **"About"** since (the id was left alone: it keys the rail grouping, the icon table, palette state and every settings-audit row, and no user ever sees it). It answers three questions on one page: what am I running (the gamescope-ritz semver, the upstream base commit, HEAD's date), what changed (`CHANGELOG.md`, compiled in), and what is it made of (the licences of everything compiled into the binary — the fork's own `LICENSE`, `THIRD-PARTY-LICENSES.md` and the Geist fonts' OFL, all compiled in and printed below the changelog). Searching the command palette for either "changelog" or "about" finds it. Code: `src/Overlay/PanelChangelog.cpp`.
- **Brightness Map** — the experimental spatial local-tone effect (`image.shaders.brightness_map`), added 2026-09-09 and removed 2026-09-14 at the user's request ("You can actually remove the brightness map experimental shader, I don't need it anymore."). It divided the picture by a low-pass of the frame's own luminance against a mid-grey target, so a dark object on a bright field was lifted independently of the object's size — the case Adaptive Gamma's Local adaptation is too coarse to resolve. **Adaptive Brightness V2**'s guided-filter base/detail operator (added the same day, see that entry above) supersedes the idea, edge-aware where this was a plain Gaussian. See `superdoc/features/shader-effects.md`'s History note.
- **Zoom** — this fork's compositor-drawn magnifier (2026-09-14; `src/Overlay/Zoom.{h,cpp}`, `src/shaders/cs_zoom.comp`, settings area `system.zoom` under MISC, keybind action `zoom` bound to `RMB` by default): a copy of the middle of the game at 1.5–5×, cut to a circle, rectangle or square with a 1 px black outline, shown while the chord is held or toggled. Built *inside* `vulkan_composite()` as layer 1 — after the bundled shaders, before the upscaler — so it carries the effects and is never scaled. The user's "projection" is the shape-cut picture; its sizes are 0..1 fractions of the game's on-screen rect. **Not** upstream's `zoomScaleRatio` (Steam's whole-screen magnifier via the `screenZoom` X property), which scales the entire output. See `superdoc/features/zoom.md`.
- **Held action** — a **keybind action** flagged `bHeld` (only `zoom` today): fires on the press that completes its **chord** as a *subset* of the held keys (so it works mid-movement), reports the release that breaks it, treats a modifier-only chord as a plain press rather than a **tap**, and never swallows a mouse button. Mouse buttons (`LMB`, `RMB`, `MMB`, `Mouse4`, `Mouse5`) became chord terms with it. See `superdoc/features/keybinds.md`'s "Held actions and mouse buttons".
- **Crosshair** — the compositor-drawn crosshair (`src/Overlay/Crosshair.{h,cpp}`, settings area `system.crosshair`, added 2026-09-05): four arms, an optional centre dot, an optional outline, an optional auto-hide while right-click is held, and an optional per-axis stretch ("Apply Scaling"). Drawn into the **HUD**'s layer, centred on the game's on-screen rect, so it composites *after* an external frame-generation layer (`lsfg-vk`) has interpolated the game — the in-game crosshair smears under frame generation, this one cannot. Distinct from the game's own crosshair and from the **Cursor** (the pointer). See `superdoc/features/crosshair.md`.
- **Profiler** — the user's own term for the perf-stats modules the **HUD** used to carry on top of the plain FPS number: CPU load, GPU load, a frametime readout, a frametime graph, a 1%/0.1%-low percentile row, and a Now Playing (MPRIS) module. Removed 2026-09-03 at the user's explicit request as feature bloat — the HUD is a single FPS integer now. The underlying frame-rate counting/timing and lag-spike detection (the raw per-frame frametime history, `FpsDisplay.cpp`'s `s_flFrametimeHistoryMs`) were kept, since a later phase builds on them; the CPU/GPU/media sampling (`src/Metrics/SystemStats.{h,cpp}`, the only consumer of which was the profiler) was deleted along with it.
- **Profile** — the settings file being edited (`~/.config/gamescope-ritz/profiles/<Name>.json`); every change is saved into it at once. **General** (`Comp`, `Casual`) or **game** (bound to one app id, listed as `[Game] Rust`); Profiles v2, 2026-09-06 — see `superdoc/features/profiles.md`, which also keeps the v1 history (the copy-and-Use model, per-game snapshots, active profile, auto-save).
- **Inherits** — a game profile's link to one general profile: it stores only the values that differ (`ponytail:` a value set equal to the parent's reads as inherited) and follows the parent live for the rest. Two levels, no chains; a parent with children cannot become a game profile; deleting a parent bakes its children.
- **Selected profile** — the outlined line in the Profiles list (`profiles.list`, the **Shell**'s Setup > Profiles area); clicking a line (Enter while hovering, or Left/Right on the band) loads it *and* is the assignment the current game remembers (`games.<AppId>.selected`), while a general pick also becomes `last_general`, what a never-seen game starts on. Create / Copy / Edit / Delete under the list act on it. There is no load or save button: selecting is loading, and every edit is saved as it happens. Code: `config::SelectProfile()`; UI: `src/Overlay/PanelConfig.cpp`.
- **Session profile** — the profile this session edits (`config::SessionProfile()`): the `--profile <name>` / `GS_RITZ_PROFILE` / `ritz_profile` override if given (session-only, created from what the session would have used when missing), else the selected profile, else `last_general`, else `Default`. Shown as every area's header badge (`[Game] Rust`, or `Casual (launch)` under an override; Appearance alone keeps `global only`) and as the Profiles area's Status row. While it is a game profile with a parent, every row of every area is *inherited* (nothing drawn) or *overridden* (a small accent dot after the label; the Inspector offers **Reset to inherited**).
- **Chord** — a keybind, in this project's own grammar: an unordered set of keys that must be held together, written `+`-separated (`RShift`, `Ctrl+Shift+O`, `LCtrl+RShift`). `Ctrl`/`Alt`/`Shift`/`Super` take either hand; `LCtrl`/`RShift`/... name one. A chord matches the **whole** held set, never a prefix of it. A chord of only modifiers is a **tap** (fires on release, only if nothing else was pressed while it was held, and is never swallowed); any other chord fires on the press that completes it and is swallowed. `src/Keybinds.{h,cpp}`, added 2026-09-08 — see `superdoc/features/keybinds.md`.
- **Keybind action** — one thing a **chord** can be bound to. There are four, each carrying exactly one chord: `shell` (Open settings, default `RShift`), `shell_alt` (Open settings (alternate), default `Ctrl+Shift+O`), `launcher` (Open launcher, default `LCtrl+RShift`) and `friends` (Open friends list, default `Ctrl+Shift+Tab`, added 2026-09-08 with the **Friends list**). A fifth action, `companion` (Open Steam chat), existed from 2026-09-08 to 2026-09-09 for the now-removed Steam chat companion — see the **Friends list** entry's history note. Stored in `global.json`'s `overlay.keybinds` — global, never per profile — and edited in the **Shell**'s Keybinds area (`setup.keybinds`). Distinct from a `gamescope_action_binding` trigger, which is upstream's client-registered binding table and is not editable here.
- **Reserved chord** — `Ctrl+Alt+Shift+O`. Always toggles the **Shell**, is not a **keybind action**, cannot be rebound, and is refused as a value for any action. It exists so that a shell chord the user can no longer type does not take the settings UI — and with it the way to fix the binding — with it. `gamescopectl ritz_keybinds_reset` is the other, independent way back.
- **Nested resolution / refresh** — the game's own resolution and paced refresh (`-w`/`-h`/`-r`; `g_nNestedWidth`/`g_nNestedHeight`/`g_nNestedRefresh`), set live by `steamcompmgr_set_nested_mode()` and shown in the Resolution area's Aspect/Resolution rows and Live-state line (`superdoc/features/resolution-and-refresh.md`). Named for the code's own `g_nNested*` prefix, per the user's instruction (requests-2026-09-07 item 4: "Use the terminology 'nested' and 'output'"). Not the same sense as **Nested mode** above (that names the whole run-as-a-window setup); this is specifically the pair of numbers Xwayland reports to the game inside it.
- **Output resolution / refresh** — the size and refresh the host actually granted gamescope's own window (`g_nOutputWidth`/`g_nOutputHeight`/`g_nOutputRefresh`), i.e. what used to be called "window" and "host refresh" in the Resolution area's Live-state line before requests-2026-09-07 item 4 renamed it. The game's picture is scaled by gamescope to fit this size; it is not requestable from the Resolution area (the window-sizing rows were removed 2026-09-06 — see that doc's "Window size" section) but is always reported, read-only, alongside the **Nested resolution / refresh** it is paired with.
- **Preview split** — the **Shaders** area's `image.shaders.preview_split` switch (added 2026-09-14, top row, above the Effects band), the user's own testing aid: *"It should only apply the shader to the right half of the screen ... so you can judge what an effect really does."* Display-only: every effect still processes the WHOLE frame (an adaptive effect's statistics are never disturbed), and `cs_effects_layer0.comp`'s final store overwrites only the left half with the raw input texel. Deliberately excluded from `NativeEffectsState_t::AnyEnabled()`, so with every other effect off it shows raw|raw at zero cost rather than forcing the pre-pass on by itself. Does not apply to a user's own ReShade `.fx` file. See `superdoc/features/shader-effects.md`'s own section.
- **Friends list** (the `system.friends` area, added 2026-09-08, narrowed 2026-09-09, click model split 2026-09-14) — this fork's own list of the Steam friends who are **in the game this session is running and in a lobby you can join**, read out of the **already-running** Steam client by `dlopen`ing its `steamclient.so` (no Web API key, no browser, no second sign-in, no app id handed to Steam, no `SteamAPI_Init`, and since 2026-09-09 no network at all), opened with the `friends` **keybind action** (`Ctrl+Shift+Tab`). Every row is marked `[Join]`. **A single click, or Enter while hovering the list, only selects a row** (outlined the way the Profiles list's `profiles.list` marks its own selection); **a double-click, or the Join verb on the selected row, actually joins** — hands the running client a `steam://joinlobby/<appid>/<lobbyid>/<steamid64>` URL and the running game moves you, relaunching nothing — **and either way closes the settings overlay the instant it fires.** Before 2026-09-14 a single click joined immediately, which the user reported as a bug (*"clicking once should just select a user in the UI, double-clicking should join them"*). `src/SteamFriends.{h,cpp}`, `src/SteamFriendsCmd.h`, `src/Overlay/PanelFriends.{h,cpp}` — see `superdoc/features/steam-friends.md`. **The whole area is hidden when this is not a Steam game** (`AvailableWhen`, no app id): no rail entry, no palette rows, and the keybind does nothing. **The Status row carries two counts** — *"3 friends in this game, 0 you can join"* — on purpose: `m_steamIDLobby`'s offset in `FriendGameInfo_t` is still unproven, a wrong offset reads as zero exactly like "not joinable", and without that first number an empty list would be indistinguishable from a broken read. **History:** until 2026-09-09 it listed every friend in *any* game, with the game's name looked up online for anything not installed locally (`overlay.friends_lookup_names`, `src/SteamAppNames.h`); the user asked for same-game joinable friends only, which made the name redundant and let the lookup — the compositor's only outbound request — be deleted. Distinct from Steam's real Friends window (which cannot be shown here at all). **History:** from 2026-09-08 to 2026-09-09 this fork also shipped a Steam chat companion — a browser window on gamescope's own Xwayland promoted to a fullscreen overlay, bound to `Ctrl+Shift+C` — which could talk but, unlike this list, could never join a friend. It was removed 2026-09-09 once this list proved it could join for real; see `superdoc/features/steam-friends.md`'s *"History: the browser companion it replaced"*.
