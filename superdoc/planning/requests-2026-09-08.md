## [x] 1. Rust: changing the resolution mid-game breaks mouse positioning

> Changing the Resolution breaks the mouse positioning in Rust.

CS2's own mid-match resolution change passed, so this is game- or state-specific; the
2026-09-07 relative-motion fix `a076916` and the 2026-09-06 warp gate `c81391e` are the
code in question.

Built, desktop-verified headless. **Reproduced with Wine**, not with the pointer code: Rust
is a Proton game, so the client is Wine, and `tests/pointer_probe_win32.c` (a Win32 program,
mingw-built, run with the system wine inside gamescope's Xwayland) showed that a nested-mode
change makes Wine put its window back to the old size and drop fullscreen. A mode **smaller**
than that window then leaves the X server confining the pointer to the new root while
gamescope maps the host pointer onto the whole window: a sample at 95% of the output reached
the game at the root corner (959,539 instead of 912,513) -- the right/bottom band of the
picture is visible but unreachable, and the cursor you see and the click the game gets
disagree there. Neither `a076916` nor `c81391e` is involved; relative motion while locked was
intact across the change (10 x dx=5 before and after, `motions_locked=0`). Fix: a focused
game window heading for a size larger than the screen is resized to the root like a
fullscreen one (`DetermineAndApplyFocus()`, `steamcompmgr.cpp`); Wine accepts the second
resize and the game gets exactly the region it can point at. Same sample after: 912,513 at
the game, equal to gamescope's own cursor. `scripts/pointer-regression.sh` 32 -> 50 checks
(`oversized-window`, `wine-mode`, `wine-lock-mode`), all green. Evidence:
`build-release/verify-shots/pointer-regression/explore-20260906-21*-wine-*` and the
`2026-09-06-22*` results. Write-up: `superdoc/features/cursor-pipeline.md`, "A window larger
than the screen".

**Laptop-verified 2026-09-08**: no sway there, so `pointer-regression.sh` itself can't run

## [~] 5. New: widen Adaptive Brightness min/max gain

> For adaptive brightness, make the min gain 0.3 and the max gain 4.0.

Both Params' ranges widened: Min gain 0.5..1.0 -> **0.3..1.0**, Max gain 1.0..2.0 ->
**1.0..4.0** (`src/Overlay/PanelShaders.cpp`). Defaults moved to the new extremes per the
plain reading of the request -- `min_gain` 0.5 -> 0.3, `max_gain` 2.0 -> 4.0
(`ConfigSchema.h`); an existing config keeps whatever it already stored, only an unset
key or a fresh install sees the new numbers. `GAMMA_MIN`/`GAMMA_MAX`/`KNEE`/`WHITE`
(`effects_curve.h`) deliberately untouched -- a separate highlight-rolloff change is
being designed against those, kept independent on purpose.

**Consequences checked, not assumed:**
- **Shadow cap loosens (min_gain).** On the bright reference scene the cap's own binding
  value moved from min_gain 0.5's 15 down to min_gain 0.3's 9 (both `p2 x min_gain`
  exactly, within float rounding) -- but the *mechanism* changed too: at 0.3 the cap's own
  ceiling (~1.503) now exceeds `GAMMA_MAX` 1.5, so `GAMMA_MAX` binds instead of the cap.
  Not crushed (9 stays well above black), but the margin is real and roughly halved.
  Visually confirmed not crushed in `adaptive-gain-2026-09-07/03-bright-mingain0.5.png`
  vs `04-bright-mingain0.3.png` -- the 0.3 capture is visibly darker on the shadow
  rectangles but neither reads as pure black.
- **Dark scene lifts much further (max_gain).** Darkest band (5) went from 50 (old
  max_gain 2.0) to 71 (new max_gain 4.0) -- a genuine improvement, still nowhere near
  clipping (highlight stays at 254, one count softer than the old 253).
- **Bright-scene highlights compress harder, not softer -- the honest downside.**
  max_gain 4.0 does not touch the bright scene (gain 0.918 unaffected either way), but
  min_gain 0.3's looser cap lets gamma reach the fixed 1.5 ceiling instead of 1.273, which
  drags every highlight number down: the 245-band figure goes 213 -> 206, white 224 ->
  218. Reported plainly per the task brief: on this scene alone the new defaults compress
  the top end *harder*.
