## [~] 1. Crosshair overlay

A compositor-drawn 4-line crosshair with optional centre dot, so an external
frame-generation layer (`lsfg-vk`, inside the game) cannot smear it — gamescope
composites it *after* interpolation. User's spec, all of it:

- **Line**: enable · length (proper 1px mode) · width · gap · colour · transparency
- **Dot**: enable · size · colour · transparency
- **Outline**: enable · width · transparency · colour
- **Auto-hide when holding right-click**: enable · hide mode *Fade out* /
  *Focus* (gap → 0 for 50% of the time, then fade for 50%) / *Shrink* (gap → 0 for
  50%, then length → 0 for 50%) · time to hide (ms)
- **Apply Scaling**: also stretch the crosshair when the game runs below output
  resolution, so it looks the way "stretch" players expect.

**Decided:** own tab `system.crosshair` "Crosshair" beside HUD; drawn into the HUD
layer (no new layer — the 6-layer budget is full and `push()` fails silently); centred
on **layer 0's on-screen rect**, not the output; release snaps back instantly (no
reverse animation); hide only fires when the click goes to the game, not the Shell.
Adds `wlserver_debug_mouse_button "273 1"` / `"273 0"` so the hide can be exercised
on the laptop without OS-level injection — it enters at `wlserver_mousebutton()`, the
same path every real backend uses.

## [~] 3. Profiles and Per-game UI rework

User: *"I need to restart the whole game to actually see a freshly created profile …
I'm almost scared to touch it. It needs a toggle for auto-saving and so on. Same for
the per-game profile part."*

**Bug, root-caused:** `SaveCurrentAsNewProfile()` enqueues the write on a background
thread and re-reads the directory before the file lands (`PanelConfig.cpp:431`→`:434`),
so the cached list — and the hash that drives rebuilds — never moves. Fix: write the
profile synchronously (precedent: `DisableOverride()`'s inline one-off write).

**Design (from the 2026-09-05 scout; row by row in its report):** a **Status** group
at the top of each area (active profile · changes since applied · where edits go ·
detected game); **Auto-save to profile** switch; **Save changes** / **Save as new** /
**Rename** / **Delete** (confirm on delete only); **Use this profile** keeps a one-step
backup and exposes **Restore previous settings**; Per-game gets **Use separate
settings for this game** (was "Override global config") and **Start from profile**,
making "this game → profile X" explicit. Plain-language help throughout.

**Decided:** Auto-save defaults **off**, dirty count always visible, the active
profile keeps its name when dirty. `Why:` on-by-default makes one profile applied to
several games change under every other game's future Use — spooky action the config
research argued against; off honours "a toggle for auto-saving" as opt-in. Extends
DECISIONS #20 (apply copies in once; auto-save copies edits back out; the profile is
still never a live source). New global-only fields `active_profile`, `auto_save_profile`.

## [ ] 4. FPS counter: measure correctly, drop the 999 clamp, new Smoothing

User: *"It shows 999 FPS in Rust, which is basically impossible. Remove that weird
999 limit. Smoothing should show a static value for 700 ms and then smoothly
transition to the next value in 300 ms."*

**Root cause (scouted):** the counter *times* individual commits and the HUD keeps
only the last sample written before each paint. When steamcompmgr drains a batch of
≥2 commits in one loop — which `lsfg-vk` guarantees — the last one has `dt ≈ 0`,
clamped to 0.1 ms → 10 000 fps → shown as the 999 clamp, in every mode.

**Fix:** **count** commits (`g_ulAppCommitCount` beside `commit.cpp:93`), compute
`Δcount/Δt`. Remove `std::clamp(nFps, 0, 999)` (`FpsDisplay.cpp:827-828`); pin the
box width to the *current* digit count, never below 3. **Smoothing** = 1 s windowed
rate, displayed integer `smoothstep`-glided from old to new over 300 ms, held 700 ms;
timer thread ticks ~16 ms only while gliding. **Immediate** = count over the last
100 ms. `per_second` is subsumed (legacy value maps to Smoothing).

**Inherent limit to tell the user:** with `lsfg-vk` at ×2 the counter shows the
*generated* rate — the compositor only sees post-frame-gen presents, same as MangoHud
loaded after the layer. Pre-frame-gen FPS is not observable from here.

## [ ] 7. Change nested resolution and refresh rate at runtime

User: *"Give the user the ability to change the nested resolution and refresh rate.
Implement a proper UI for that!"* Three things, possibly separable: the **output**
window size (`-W/-H`, what the host compositor sees), the **game's internal**
resolution (`-w/-h`, what Xwayland reports to the game via XRandR), and the paced
**refresh** (`-r`, the fake vblank rate and the mode's reported refresh). Scouting
first: which of the three gamescope can change live without restarting Xwayland,
how the host window resize path already works, and what the UI must say when a
change needs a game restart to take effect.

**Scouted 2026-09-05 — all three are live, none needs a restart of Xwayland or
gamescope:**
- **Internal resolution + refresh** share one existing call,
  `wlserver_set_xwayland_server_mode(idx, w, h, mHz)` (`wlserver.cpp:4324`, under
  `wlserver_lock()`): new mode on the headless output → Xwayland updates RandR →
  `RRScreenChangeNotify` → fullscreen windows are force-resized by focus code
  (`steamcompmgr.cpp:4480-4495`). This is Steam Deck's own knob (X atom
  `GAMESCOPE_XWAYLAND_MODE_CONTROL`), just not reachable from the fork's UI. The
  atom path does not update `g_nNestedWidth/Height`; the fork setter must. The
  vblank timer re-reads `g_nNestedRefresh` every cycle, so refresh follows a plain
  write — but SDL's `g_nOldNestedRefresh` static must be updated or focus-regain
  reverts it. Windowed games with size hints keep their size; games that read the
  mode list once need a relaunch — honest wording: "most games switch instantly; a
  few only list it after a restart".
- **Output size** can only be *requested*: `SDL_SetWindowSize` on the SDL thread /
  `libdecor_state_new` on Wayland. A tiled Hyprland window answers with its own
  configure. The UI reads back the real `g_nOutputWidth/Height` and says so.
- **UI:** new `display.resolution` area after Upscaling — resolution preset Choice
  + Custom width/height Steppers with aspect lock; refresh Choice (Follow host / 60 /
  90 / 120 / 144 / 165 / 240 / Custom); output-size Choice marked "host decides";
  a Facts row "Game sees W×H @ R Hz · window W×H · host R Hz". Nested-only in
  phase 1 (gate on `GetNestedHints() != nullptr`); DRM later via `GetModes()` and
  the dynamic-refresh atom.
- **Persist** resolution and refresh in `GamescopeSettings` (`0 = as launched`);
  `apply_ritz_config_to_startup_state()` runs before getopt, so **CLI wins for
  free**. Do not persist output size — window rules are the right tool.
- **Not achievable:** forcing a tiling host to honour a window size; changing the
  host monitor's refresh; guaranteeing a running game adopts the new mode.
