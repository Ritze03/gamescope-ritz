headless, both edit orders (`build-release/verify-shots/paneldisplay-routing/

config layer in `tests/test_config.cpp`. `superdoc/features/profiles.md`'s
routed-write-merge ceiling paragraph updated -- narrowed to a coding-discipline
residue, no longer a known reachable defect.

**Closing-pass finding, 2026-09-06 (blocking, not fixed here -- src/ out of scope for
this pass):** `a6c413d` regressed `scripts/pointer-regression.sh`'s `unlocked-resync`
check (16/20 -> 4 fails, bisected and reproduced deterministically twice; full trace
in `build-release/verify-shots/closing-pass-2026-09-06/pointer-regression-bisect.txt`).
Cause: `SetScaler()`/`SetFilter()`/`SetSharpnessUiPercent()`/`ApplyNestedMode()` each
assign their live global *before* calling `Cfg()`; on the first `Cfg()` call after a
generation bump (startup, or right after a profile select, before Display has drawn),
the now-unconditional `PushCachedSettingsToLiveState()` re-applies the just-loaded
*pre-edit* value and clobbers the assignment the same setter made one line above --
the cached/saved value is correct, but the first edit's live effect is silently lost
until an identical second edit repeats it (same generation, no re-push). Practical
impact: the first Upscaling/Filter/Sharpness/Aspect-or-Resolution change of a session,
or right after a profile select, may not visibly apply until repeated. Needs a real
fix in `src/Overlay/PanelDisplay.cpp` (reorder each setter to mutate through `Cfg()`
before the live global, as `SetFpsLimit` already does, or make the live push a no-op
when nothing changed) before this item can move past `[~]`.

## [~] 12. Crosshair: slider grab handle too wide for Outline Width, Dot Size, Line Width

> Crosshair: the slider grab handle is far too wide for Outline Width, Dot Size and
> Line Width; other sliders are fine.

**Done, desktop-verified, laptop pending.** `1ab8d39`. Root cause was ImGui's own
`SliderBehaviorT`: for a non-decimal data type (every `SliderInt`) it widens the grab
past `GrabMinSize` on purpose, "to represent one unit" of a coarse range -- Outline
Width (1..8), Dot Size and Line Width (1..16) all hit this; every other slider in the
kit is float-backed and never did. `SliderGrab()` (Controls.cpp) now recentres the
grab to the kit's constant width AFTER `SliderBehavior` has already resolved the
frame's click/drag/keyboard step from its own wider one, so only the drawn width
changes. Extracted as `ui::controls::ConstantWidthGrab()`, pure arithmetic pinned by
four new `test_overlay_ui.cpp` cases without an ImGui context. Before/after on
Crosshair > Line > Width:
`build-release/verify-shots/gui-2026-09-06/07-slider-crosshair-before-crop.png` vs
`07-slider-crosshair-after-crop.png` (3x nearest-neighbour crops of the same row).

## [~] 14. Crosshair: scaled crosshair renders wrong (thickness/blur/gap)

> Crosshair: the scaled crosshair does not get properly thicker and sub-pixel
> blurry and the gap is wrong; render it normally, then scale it according to the
> other settings.

**Done, desktop-verified, laptop pending.** `b92a4f7`. Cause (measured, not the
geometry): the raster was drawn as an ImGui image quad, and everything ImGui draws goes
through its `SRC_ALPHA` blend, so every partially covered edge pixel landed
premultiplied and the composite -- which reads a HUD texel as straight alpha -- showed
it at coverage squared: a 1 px line at 2x (75 %/25 % rows) came out at 56 %/6 %,
`(23,169,23)` for pure green over 51, a dimmer *thinner* line whose 56 % end pixels
made the gap read a pixel wide on each side. The stretch itself was already right
(arm start 658 = 642 + 8*2). Fix: build and rasterise at game resolution exactly as
before, stretch on the CPU (`crosshair::ResampleToOutput()`, bilinear, premultiplied,
the same texel-centre mapping), and copy the straight-alpha result straight into the
HUD texture before its render pass (which then LOADs instead of clearing, so the
readout still draws over it) -- no ImGui quad, no private texture. Measured headless
(`crosshair-scaled`, 640x360 client stretched 2x onto 1280x720, width 1, gap 8,
length 12): arms **24** long, inner ends **34** apart (2*16 + the 2 px centre column),
**2** wide at >= 50 % coverage, edge coverage **0.25** beside each arm and **0.19**
(= 0.25 * 0.75) past each end -- the bilinear model; Apply Scaling off on the same
instance: gap 8, length 12, exact. The 1:1 pixel path's checks are unchanged (all four
arms `(0,255,0)`, gap background, outline black) and inversion re-measured
`(251,251,251)` over 51 with the crosshair on and off; all 30 checks pass. Captures:
`build-release/verify-shots/crosshair-2026-09-06/11-scaled-old-vs-new-zoom8x.png`
(left: the old quad path, thin dark-green arms; right: now, bright 2 px arms with soft
