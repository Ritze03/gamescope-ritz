## [x] 1. CS2 in-game mouse STILL drifts back to centre

> Still broken. Same behavior.

The 2026-09-06 fix (`c81391e`, gating warps while a pointer lock is active) was
verified against a Wayland client holding `zwp_locked_pointer`; CS2 runs under
Xwayland, so the emitter or the lock detection differs there. Re-root-cause on the
Xwayland path.

**Reproduced headless, with the binary the user tested** (`tests/pointer_grab_client_x11.c`,
native SDL3 in relative mode under gamescope's Xwayland -- CS2's stack -- with an XI2 tap):
the `c81391e` client locked *before* it ever saw a pointer event; CS2 is a **menu first**.
Xwayland feeds absolute motion through one X slave device and relative motion through
another, and the master pointer copies the classes of whichever posted last; SDL3 caches
the master's axis mode at the first raw event it sees (in the menu) and never refreshes
it. This fork's `32b98bb` (2026-08-28, "relative only while locked") made the menu
absolute-only -- and with force-grab off the host-sample warp path always was -- so SDL3
cached the master as *absolute* and **differenced** the match's relative deltas: 10
injections of `dx=5` after 4 menu samples reached SDL as one `xrel=-592` (5 minus the last
menu position), then nothing, then a backwards kick on each change of direction. Not an
absolute event at all, which is why the warp gate could not touch it.

**Fix.** Relative motion accompanies every movement again -- `wlserver_mousemotion()`
unconditional (upstream verbatim), and `wlserver_mousewarp()` sends the clamped travel as a
relative event before its absolute notify (covers force-grab off, which upstream never did).
Xwayland then routes both halves through the relative slave, posts no second raw event, and
the master never changes device. `wlserver_pointer_stats` gains `relatives=`
(`relatives >= motions` always). The `c81391e` gate is kept.

**Desktop-verified** (headless, private sway): pre-fix `axis0=abs`, 10 x `dx=5` -> one
`xrel=-592`; fixed `axis0=rel`, 10 x `xrel=5.0`, 5 x `yrel=7.0`, by ConCommand and through a
real virtual host mouse (`tests/virtual_pointer_tool.c`, `zwlr_virtual_pointer_v1` into the
private sway) with force-grab off and on. `scripts/pointer-regression.sh` grew `x11-menu-lock`,
`x11-locked-abs`, `x11-host`; all checks pass. Evidence:
`build-release/verify-shots/pointer-regression/x11-explore-20260906-*`. Docs:
`cursor-pipeline.md` "The device SDL3 remembers". CS2 itself cannot run here -- laptop
check below.

**Laptop-verified 2026-09-06.** Built `tests/pointer_grab_client_x11.c` on the laptop
itself (SDL3/X11/XI dev packages present; no meson target had existed for it there
before) and ran the x11-menu-lock/x11-locked-abs sequence directly against
`gamescope --backend headless`: after a 4-sample menu the client locks; 10 relative
injections all arrive as `xrel=5.0` (not differenced); the cached master axis reads
`rel`; `wlserver_pointer_stats` reads `relatives=14 >= motions=4` and, the key
assertion, `motions_locked=0` throughout, including across 6 absolute samples sent

## [x] 8. Spinners

> When manually editing a spinner, it selects the element in the inspector rail,
> even when it was clicked in the main part of the GUI (when it shows the element

**Desktop-verified headless, laptop pending.** `412d5a9`. Reproduced first, as asked,
before changing anything: `DrawEntryRow` draws the currently-selected Entry TWICE a
frame -- once as the Sheet's own row, once again inside the Inspector's "own row" copy
at the top of its VALUES block -- and both calls share the exact same `Id()`.
`s_sEditingText` (which field is open) was keyed by that id alone, with no way to tell
the two draws apart. Sequence: clicking the Sheet's Stepper number sets the global to
that id on the SAME frame; the Inspector's copy, drawn moments later that same frame,
reads the just-set global back as "I am the one being edited" too, opens ITS OWN field,
and calls `SetKeyboardFocusHere()` -- which wins, because the Sheet's own field does not
open (and does not ask for focus) until the FOLLOWING frame, by which point something is
already active. Net effect: the visible caret ends up in the Inspector's copy, not the
Sheet field actually clicked -- exactly the report's "even when it was clicked in the
main part of the GUI." Fixed the same way `s_eOpenDropdownRegion` already fixed the
identical disease for dropdowns: a companion `s_eEditingRegion` qualifies every read and
write of `s_sEditingText`, so the Sheet's field and the Inspector's copy of the same id
are independently open/closeable, and the Inspector's own-row `DrawEntryRow` call
discards its return value entirely (see item 9), which is what keeps an edit made
*inside* the Inspector's copy from re-selecting anything or resetting the Inspector's
own scroll/focus.

## For the user to test

Everything below is built, desktop-verified headless, and laptop-verified (mechanism
and, where the environment allows it, visuals) -- see each numbered item above for the
evidence. What's left needs your own machine, a real game, or your own eyes on a
judgement call a script can't make.

1. **CS2 in a match -- the mouse fix.** Launch CS2 through the new build, force grab
   cursor **off** (the report's setup). Move the mouse in the menus, then enter a match
   or a practice map. Expected: the view follows the mouse only -- no jump when play
   starts, no drift or snapping back towards the centre, no kick on a change of
   direction. Repeat with force grab cursor **on**. If it still drifts, run this once
   while in the match and once in the menu and paste both lines:
   `gamescopectl wlserver_pointer_stats` (from a terminal, with
   `GAMESCOPE_WAYLAND_DISPLAY` set to the gamescope socket -- `gamescope-0` when it is
   the only one). Reading guide: in the menu `motions` and `relatives` advance together
   as the mouse moves; in the match `constraint=locked`, only `relatives` advances, and
   `motions_locked` stays 0. `relatives` frozen in the match = the host never confirmed
   gamescope's pointer lock (a Hyprland/backend problem, not this one); `motions_locked`
   above 0 = an absolute emitter still unknown.
2. **Crosshair layout.** Open Misc > Crosshair at a normal window size. Check the left
   column reads Crosshair, Line, Dot and the right column reads Outline, Auto-hide,
   Scaling, and that nothing looks cramped.
3. **Adaptive Brightness mode.** Open Display > Shaders. Adaptive Brightness should be
   a plain on/off switch in the row list; select it and confirm Mode (Whole image /
   Dynamic) sits in the side panel with the other six params, and the panel's header
   reads "PARAMETERS 7 of 7".
4. **Resolution: the Custom flow and the live line.** Open Display > Resolution. The
   size dropdown should not list a "Custom" entry of its own. Set Aspect to Custom and
   confirm the Width/Height fields become editable and the Resolution row shows its own
   "Custom" placeholder. Check the Live state line reads "nested `<res>@<refresh>` ·
   output `<res>@<refresh>`" with real numbers, in every aspect.
5. **Overlay opacity at 1.0.** Open Settings > Appearance and set Window transparency
   to maximum (1.0). The settings window should be completely solid -- no hint of the
   game showing through anywhere behind it.
6. **Accent swatches.** Open Settings > Appearance. Count nine preset colour buttons
   under the hue slider, and check the first and last line up with the two ends of the
   slider itself rather than sitting inset from them.
7. **Editing a row and seeing the inspector follow.** Anywhere in the settings, click a
   switch, slider, or stepper on a row that is *not* currently selected. Confirm the
   row highlights and the side panel switches to it in the same click, and that typing
   into a stepper's number opens the cursor where you clicked rather than in the side
   panel's copy of the row.
