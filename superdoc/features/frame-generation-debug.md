# Frame generation: Debug options

Part of [Frame generation](frame-generation.md). Test views and readouts for judging what frame generation does. `Why:` the user asked for them on 2026-11-23 to see what frame generation does (filtered UI, only the generated frames, where motion was found, a stats overlay).

## The switch

The row **Debug options** (`framegen.debug`, a switch, default off, never greyed, in group "Frame generation" beside **Expert settings**) shows the group **Debug**, the last group of the area (after "Motion search"). While the switch is **off, everything in the group is off**: `config::FrameGenEffective()` (`ConfigManager.cpp`) hands the host `debug_only_generated = false` and `debug_stats = false`, whatever is stored; the stored values are kept and act again when the switch goes on. Persisted per profile, like Expert settings (there is no session-only mechanism). The rows are shown with `Entry::ShownWhen(DebugOn)`, so they are also absent from keyboard navigation and the command palette while the switch is off, and greyed with "frame generation is off" while frame generation is off.

| Key | Default | Row |
|---|---|---|
| `framegen.debug` | false | "Debug options" (master switch) |
| `framegen.debug_only_generated` | false | "Only generated frames" |
| `framegen.debug_stats` | false | "Stats overlay" |

Additive (2026-11-23), schema stays 5; absent or wrong-typed loads false.

**The path to the renderer.** The packed host `Config` word is full, so the debug values travel in their own atomic, `fghost::DebugConfig` (`FrameGenHost.h`; `SetDebugConfig()` / `GetDebugConfig()`), packed by `PackDebug()` in `src/FrameGen/FrameGenDebug.h` (bit 0 only generated, bit 1 stats, bits 2-5 `view`, the Debug view row's index, see "Debug view"). `PanelFrameGen.cpp`'s `PushToRenderer()` pushes the EFFECTIVE values, on every edit, load and profile switch.

## Only generated frames

Shows only generated images; the game's own frames are skipped on screen. With Priority Low latency at fixed 2x the picture then updates at half the rate (a generated image, the same one again, a generated image, ...); at 3x it is gen, gen, held. With a Target above what the game delivers a held image can repeat several ticks. While nothing is generated (pass-through, inert, frame generation off) the game's frames show, so the picture never freezes.

**Design** (`RecordBaseLayer()`, `FrameGenHost.cpp`, at the very end, after the stale-guard block and before the submit). The pacer is not touched and the real tick is NOT skipped: its paint still does the ring copy, the observe and the pair bookkeeping that later pairs and UI protection need. Only the image that is returned changes:

1. A tick that returned a generated output (`!IsRealTick`) stamps its pool slot as the "last generated" (`Host_t::nLastGenSlot`, `ulLastGenOutId`, `ulLastGenNs`) and bumps that slot's `ulUse`.
2. A **real tick** (`IsRealTick(prevId, t1)`: no pair, or `t1 >= 1`, which is how a Motion-blurred real frame looks) shows that slot's texture instead, if `ShouldHoldGenerated()` (`FrameGenDebug.h`) agrees: option on, the interpolator live, the slot still valid with the same `outId`, and the last generated image not older than `kHoldMaxNs` (100 ms) and the pacer's own `GetPacingStatus().generating` set (a status not older than 500 ms). It bumps `ulUse` again.

`Why` in `RecordBaseLayer()` and not in the pacer: the pacer's decision drives the ring copy and the observe; dropping the real tick there would starve the ring and the UI-protection history. `Why` the `ulUse` bump: the output pool has three slots and `PickOutSlot()` is LRU; a held image must stay the most recently used so the next synth does not overwrite an image a composite still reads. `Why` the 100 ms cap and the `generating` check: a stalled generator, a scene cut or a stretch where the cost guard passes frames through must not keep an old generated image on screen; the pacer flag ends the hold at once (it is republished about every 250 ms, so it can lag), the cap bounds that lag (100 ms is a 10 fps game's frame; slower games show the real frames). The hold is skipped when the interpolator is not live (`H.bLive`) and for inert or pass-through requests, which return before the hold code. `DropFrames()` / `InvalidateOutputs()` clear slot validity, so a reset or a size change drops the hold.

**When it has an effect: Priority matters.** A "real tick" exists only where the pacer shows the game's own frame (no pair, `t = 1`). With Priority **Low latency** a fixed 2x alternates generated, real, generated, real, so Only generated frames shows each generated image twice and the shown rate stays 2x the game's. With Priority **Smoothness** (the default) the pacer already plays every shown frame as a synthesised image between the pair (phases such as 0.4 and 0.9), real frames are shown only in pass-through stretches, and the option changes almost nothing there. Smoke at fixed 2x with a 30 fps client, Low latency: real and generated ticks about 1:1, every real tick held (counter lines `100 real ticks shown ... (of 101 real, 100 generated ticks)`), shown rate 60 fps with the option on and off.

**Known side effect:** the judder meter's content time still assumes the real frame was shown, so judder numbers are wrong while the option is on. Motion blur together with Only generated frames (a blurred real frame counts as a real tick) is designed for but was not run.

## Stats overlay

The row only switches it (`debug_stats`; `fghost::GetDebugConfig().stats`, wired to `fgstats::SetEnabled()` in `PushToRenderer()`). It is drawn by `src/Overlay/FgStats.{h,cpp}`; see the section below.

Rows of text in the top left of the picture: line 1 the motion version (V3 Hybrid with its variant, `Fluidity(off)` when the blend is selected but not running; `motion V3.5` or `motion V3.5(off)` after it when V3.5 is requested), the quality and the format tag; line 2 game fps -> shown fps, the effective multiplier (or "passing through") and the mode (fixed Nx / target fps / display refresh); line 3 the added delay in ms and the frames per second the host discarded (nested Wayland only, else `-`); line 4 the library's GPU times (estimate, synth, pair, UI protection, ms); line 5 the UI protection mode (Whole screen V2 by that name); line 6 `not generating: <reason>`, only when there is one. With frame generation off it is the single line `frame generation off`; a missing number prints `-`, never 0. The text is refreshed at most 4 times a second. Formatting is pure (`FormatLines`) and unit-tested.

`Why` it shares the HUD's layer: it draws into the same draw list and texture as the FPS readout and the crosshair, so it costs no extra layer slot (6 at most; another one forces a full composite), and frame generation never sees that layer. It is NOT part of the HUD (the Profiler was removed at the user's request on 2026-09-03; the HUD stays a plain FPS integer): own files, no HUD setting. A top-left HUD readout pushes it below the readout. `Why` `fghostshown::TakeRates()` is not used: its function-static baselines belong to the status line; the overlay keeps its own previous raw counters. `Why` the draw-time mean and max are missing: `CVBlankTimer::TakeStats()` resets what it reads. It is not in `gamescopectl screenshot` (screenshots exclude the HUD layer).

Test aids: the ConVar `ritz_fg_stats 1` shows it whatever the switch says; `gamescopectl log_fgstats debug` logs the text when it changes. Not covered so far: the HUD's Inverted colour mode together with the block, and repaint while the game is idle with only the overlay on.

## Debug view

*2026-11-23, library `ce8b383`; the UI removed fill below since `bfaade7`.* The first row of the group **Debug** (`framegen.debug_view`, a Choice, default Off): the library draws one test picture onto the **generated** frames, as its last pass (after the synthesis and the UI patch; with Motion blur once, after the average). The game's own frames are never marked, and frames that are passed through (inert, cost guard, scene stretches, frame generation off) show nothing, so a view that seems to flicker is the real frames between the generated ones (use **Only generated frames** with Priority Low latency to see only marked frames). The Choice's labels are longer than 8 characters, so it measures into a dropdown (`superdoc/ui/STYLING-GUIDE.md`).

| Value (stored string, row index) | Library `DebugView` | Crosshair / Whole screen | Crosshair V2 / Whole screen V2 |
|---|---|---|---|
| Off (`off`, 0) | `Off` (0) | nothing, byte-identical, nothing created | same |
| UI highlighted (`ui_highlight`, 1) | `UiMask` (2) | pasted pixels magenta, the feathered ring weaker magenta, a 1 px yellow outline of the box | pasted pixels magenta, pixels confirmed as UI but changed in this pair (not pasted) cyan, yellow box outline (the whole frame's edge for Whole screen V2) |
| UI removed (`ui_removed`, 2) | `UiClean` (3) | no colour, no outline: the library's clean copy of the newest real frame (UI filled in from its surroundings, what the estimate works on) replaces the generated picture over the work rectangle (Crosshair) or the whole frame (Whole screen). That is a game frame, not the interpolated picture | no clean copy exists: every pixel of the box's work rectangle whose V2 mask byte is non-zero (pasted and confirmed-but-changed, exactly the pixels UI highlighted tints) is replaced in the generated frame by an average of nearby non-UI pixels: 8 directions, the first unmasked pixel within `uiInpaintReach` (default 12, 1..16), weights 1/distance^2. No colour, no outline |
| Motion map (`motion`, 3) | `Motion` (1) | tint by motion | same |

**UI removed, in detail (pin `bfaade7`).** In Crosshair and Whole screen the view is a real game frame with the UI filled in, so it is "as frame generation uses it". In the two V2 modes the fill is made **only for this view**: Crosshair V2's motion search and colour passes see the real frames with the UI in them, so the view shows what a fill would look like, not what frame generation uses. A masked pixel with no unmasked pixel within the reach stays as it is, so a UI area wider than twice the reach (24 px at the default) keeps its middle: thin elements (crosshair, text strokes, lines) go completely, a solid block loses its masked pixels only. What is filled is what the detector masks: a headless run (a 60 x 40 px solid white block, a crosshair and thin strokes on a scrolling grey background) showed Crosshair V2 masking the thin elements fully but only the corners of the solid block, so the block's middle and straight edges stay (Whole screen V2 the same). In Crosshair and Whole screen the clean copy of the same block left a 40 x 20 px middle. Cost the library measured (8-bit, 2x, box = whole frame, per real pair against view Off): under 0.1 ms at 1080p and 1440p with about 1 % of the frame masked, +0.24 ms at 1080p with 40 % masked (a paused or static picture; 1440p not measured). The view still takes one UI-ring set; the fill is the same `debug_ui` shader (one more mode), so no new build entry, pipeline or guard, and `sizeof( Settings )` stays 164. Formats: 8-bit, 10-bit, fp16; nothing for Nv12 / P010.

The row's order differs from the library enum's on purpose (the UI views first); `LibraryDebugView()` in `FrameGenDebug.h` is the one mapping, pinned by a unit test, and `FrameGenHost.cpp` static-asserts the enum values and `sizeof( framegen::Settings ) == 164`. UI protection Off, or a pair that was not observed under the active mode, draws nothing for the two UI views. Nv12 / P010 accept the value and draw nothing (the host runs Rgba8 / Bgra8, 10-bit and fp16).

**Motion map.** Tint by the prev -> curr displacement in **full-resolution pixels**, the same unit in every motion version: none up to `flowScale` pixels (2 px at the default), rising smoothly to about 60 % tint at 16 px; hue = direction (HSV wheel, red = +x, y down). Untinted pixels are bit-exact the Off picture. It shows the motion FIELD, not the synthesis' own corrections. Nothing is drawn on a V3 scene cut; there is no fallback marker in any version. In HDR formats the tint colours are scaled down so a view does not flash at full brightness.

**Cost** (the library's measurement, 1080p, 2x): Off unchanged; Motion about +0.012 to +0.025 ms per real pair; the UI views within noise.

**Where it enters the library** (`ApplyDebugView()`, `FrameGenHost.cpp`, called at the end of `EnsureReady()` and in its first-init early return): a separate `setSettings()` on top of the library's CURRENT settings, keyed by `Host_t::nDebugViewHandled` (the row's index last handled). A view change is a runtime change: no `reconfigure()`, no estimate dropped, so pacing and the output ring are not touched. The effective view is read from `fghost::DebugConfig::view` (`FrameGenEffective()` already turned it off while Debug options is off), which `PushToRenderer()` fills with `DebugViewFromKey()`.

**Refused view.** The first time a view is on, the library creates its pipeline inside `setSettings()` and returns false, settings unchanged, if that fails or the debug shader variants of this format are not built in. The host then logs once per change `frame generation: debug view <name> not available: <settingsError()>`, publishes `DebugViewRefused()`, sets the view to Off, and does not retry until the row changes (or after a restart of the interpolator, e.g. a game format change). The other settings are unaffected because the view never travels with them. The stats overlay then says `view: <name> (not available)`; a successful change logs `frame generation: debug view <name>`.

**Where it shows.** Stats overlay: a line `view: Motion map` after the UI-protection line. Capture / watch headers (`ritz_fg_capture`): a token ` view=motion` / `view=ui_highlight` / `view=ui_removed` after the blend token (only while a view is drawn), so a capture is not mistaken for the normal picture. `gamescopectl screenshot` leaves out the HUD layer but contains the generated frame with the view.

**Build trap.** `framegen.cpp` includes a debug shader set only when all four of its headers exist (`__has_include`: `FG_HAVE_DBG`, `FG_HAVE_DBG_RGB10`, `FG_HAVE_DBG_F16`). A partial or missing list still BUILDS; the view is then refused at runtime with the message above. `src/meson.build` therefore lists, from `gpu/shaders/`: `debug_motion`, `debug_ui`, `debug_motion_v2` (`-DDBG_V2=1`), `debug_motion_v3` (`-DDBG_V3=1`) plain, and the same four with `-DFG_FORMAT_RGB10=1` / `-DFG_FORMAT_F16=1` as `<name>_<fmt>_spv.h` (12 headers; none for nv12 / p010). Proof they are in the build: the view is accepted in an 8-bit and a 10-bit run (no "not available" line). No existing shader's SPIR-V changed with the `ce8b383` pin (md5 of every generated `*_spv.h` before and after: only new headers). The `bfaade7` pin changes one shader source, `debug_ui.comp`, so only the three `debug_ui*_spv.h` headers differ (plain / rgb10 / f16); the generated header list (130 `*_spv.h`) is unchanged.

**Descriptor ring.** A UI view takes up to 2 more sets of the library's UI ring (`kUiSets` = 64) per synth, 4 per synth with the patch; the library refuses a synth that does not fit. The host records at most one synth per command buffer (one composite = one request = one output, `beginFrame()` once per command buffer) next to at most two observes (an observe and the estimate's implicit one, 2 sets each in Whole screen), so at most about 8 sets per `beginFrame()`: the ring cannot overflow in any multiplier, Target or Motion blur configuration (Motion blur's `recordSynthBlur` is one call per output, the patch once). Should the ring ever refuse, the existing "recordSynth refused" path shows the real frame.

**Motion blur.** There is one interpolator for Frame generation and Motion blur (the blur's own Motion version / Quality only change settings), so the view acts on blurred outputs too, whatever the blur's own configuration; the Motion map then shows the motion of the average's interior samples.

`Why` UI removed never draws a colour (2026-11-23): the user said "UI removed shouldnt add any highlights. It should just remove the UI, by replacing it with nearby pixels (like it does for the frame gen)"; with `ce8b383` the V2 modes fell back to the highlight picture because Crosshair V2 keeps no clean copy, hence the library's fill for that view. `Why` one Choice and not three switches: the library draws one view at a time. `Why` the library draws the views: the UI masks, the clean copies and the per-frame motion field are inside the library and not reachable from the host. `Why` a separate `setSettings()` and not the packed-config key: the key is full, and a view change must never take the reconfigure path or drop the estimate.
