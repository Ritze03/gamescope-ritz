# External Control — `gamescopectl` and `gamescope_control`

The external-control surface: how a process **outside** gamescope (the `gamescopectl` CLI, or the Steam client on the user's behalf) queries and drives a running gamescope session — screenshots, display sleep, color "looks", performance stats, refresh-cycle targeting, and arbitrary convar execution. Everything here rides on two of the private Wayland protocols indexed in [wayland-protocols.md](wayland-protocols.md): `gamescope_control` (structured, versioned requests) and `gamescope_private` (an open-ended debug/convar channel).

## How it works

- **Two separate protocols, two separate purposes.** `gamescope_control` (`protocol/gamescope-control.xml:32`) is the stable-ish, feature-gated request surface described below. `gamescope_private` (`protocol/gamescope-private.xml`) is explicitly documented as unversioned ("no stable ABI is guaranteed... it is versioned with gamescope") and exposes exactly one request, `execute(cvar_name, value)`, plus a `log` event that streams gamescope's console output back to the caller. *Why split them:* `gamescope_control` is the surface other software (the Steam client) is meant to depend on across gamescope versions; `gamescope_private` is deliberately the "debug back door" — it can execute *any* registered convar/command, which is far more powerful and far less stable a contract.
- **`gamescopectl`** (`src/Apps/gamescopectl.cpp:291 main`) is the reference client for both. Run with no arguments, it binds only `gamescope_control` (`RunGamescopeCtl`, `:246`, `bInitControl = argc < 2`) and does two `wl_display_roundtrip()`s to collect the `feature_support` and `active_display_info` events before printing an info dump. Run with arguments, it instead binds `gamescope_private` and calls `gamescope_private_execute(m_pGamescopePrivate, args[0], args[1])` (`:131`) — i.e. `gamescopectl <cvar> [value]` is a thin wrapper over convar execution, not a wrapper over the individual `gamescope_control` requests like `take_screenshot`/`set_look`. Those structured requests exist on the protocol for other clients (notably the Steam client) to call directly over Wayland; `gamescopectl` itself only *reads* `gamescope_control` events (feature list, screenshot-taken notification), it does not send `take_screenshot`/`display_sleep`/`set_look` requests itself. See the convar system this drives on [scripting-convars.md](scripting-convars.md).
- **Session discovery**: both paths connect to `GAMESCOPE_WAYLAND_DISPLAY` (falling back to `"gamescope-0"` if unset, `gamescopectl.cpp:86`) — the same env var the [Vulkan WSI layer](vk-wsi-layer.md) uses, so any tool wanting to reach a specific gamescope instance uses this one variable consistently across the codebase.
- **Feature discovery is explicit and versioned.** On bind, the server enumerates every feature it supports via repeated `feature_support` events terminated by a `done` sentinel (`src/wlserver.cpp:1402-1409`, `gamescope_control_send_feature_support(..., GAMESCOPE_CONTROL_FEATURE_DONE, 0, 0)` last). Each feature (`protocol/gamescope-control.xml:35 enum feature`: `reshade_shaders`, `display_info`, `pixel_filter`, `refresh_cycle_only_change_refresh_rate`, `mura_correction`, `look`, `perf_query`) has its own `version`/`flags`, so a client can probe what a given gamescope build supports before calling into it — most requests below were added in later protocol `since=` versions (2 through 6), not all present from v1. *Why:* Steam and gamescope ship on independent cadences; feature+version probing lets the Steam client stay compatible with older gamescope builds instead of assuming every request exists.

### Key requests

- **`take_screenshot`** (`protocol/gamescope-control.xml:94`, since v3) — `(path, type, flags)`. `type` selects how much of the compositing pipeline the screenshot captures (`screenshot_type` enum: `base_plane_only`, `all_real_layers`, `full_composition`, `screen_buffer` — see the enum at `:83`). Server-side it's handled by `gamescope_control_take_screenshot` (`src/wlserver.cpp:1160`), which forwards straight into `gamescope::CScreenshotManager::Get().TakeScreenshot(...)`; completion is reported back asynchronously via the `screenshot_taken` event (fired from `src/steamcompmgr.cpp:3311`).
- **`display_sleep`** (`:114`, since v4) — `(display_type, flags)`, where `display_type` picks internal/external display and `flags` is `sleep` or `wake` (mutually exclusive per the protocol doc). Handled by `gamescope_control_display_sleep` (`src/wlserver.cpp:1173`), which calls `drm_sleep_screen()` per selected display type — this is a DRM-backend-level power operation, so it only does something meaningful on the [DRM backend](backend-drm.md).
- **`set_look`** (`:124`, since v5) / **`unset_look`** (`:131`) — sets or clears a display "look": a 3D LUT (`.cube` format) applied per EOTF (`Gamma22`/`PQ`), passed as **file descriptors** (`lut3d_g22`, `lut3d_pq` — the protocol hands over open FDs, not paths, so the LUT data doesn't need to be independently readable by the compositor process). Handled by `gamescope_control_set_look` (`src/wlserver.cpp:1242`), which loads each FD into a `lut3d_t` via `LoadCubeLut`, updates `g_ColorMgmtLooks[EOTF_...]`, and marks a repaint. "Look" is project vocabulary — see [../meta/TERMINOLOGY.md](../meta/TERMINOLOGY.md). *Why FDs and not paths:* it lets a client (e.g. Steam) hand over LUT contents it generated in-memory or from a location the compositor process may not have direct filesystem access to. Note there is also a `set_look` **console command** (`src/wlserver.cpp:1189 cc_set_look`) with the same effect for local/debug use via `gamescope_private`'s `execute` — the protocol request and the convar are two independent entry points into the same underlying state.
- **`request_app_performance_stats`** (`:135`, since v6) — `(app_id)`. Handled by `gamescope_control_request_app_performance_stats` (`src/wlserver.cpp:1304`), which just queues the requesting `wl_resource` in `wlserver.app_perf_requests[app_id]`; the actual `app_performance_stats` event (frametime in nanoseconds, split hi/lo across two `uint` args since Wayland has no native 64-bit type) is sent later, once, whenever `wlserver_app_presented()` (`src/wlserver.cpp:1310`) next fires for that app — this is a one-shot "next frame's stats" subscription, not a stream; a client re-requests it per sample.
- **`set_app_target_refresh_cycle`** (since v2) — lets a client ask gamescope to target a specific FPS/refresh rate for the active app, with flags to scope it to internal/external display, allow refresh-rate switching, or restrict the change to refresh rate only (no frame-limiter cap change). Forwards into `steamcompmgr_set_app_refresh_cycle_override()` (`src/wlserver.cpp:1147 gamescope_control_set_app_target_refresh_cycle`).

## Using it

- **Info dump:** `gamescopectl` with no arguments — prints active display info (connector name, make/model, flags, valid refresh rates) and the full feature-support list with per-feature version/flags.
- **Convar execution:** `gamescopectl <name> [value]` — e.g. reading or setting any convar registered with the `ConVar`/`ConCommand` system (see [scripting-convars.md](scripting-convars.md)); output streams back over the `gamescope_private` `log` event and prints to stderr as it arrives (`Wayland_GamescopePrivate_Log`, `gamescopectl.cpp:198`). Use `gamescopectl help` to list available commands/convars from the target session itself.
- **Structured requests** (`take_screenshot`, `display_sleep`, `set_look`, `request_app_performance_stats`) are not exposed as `gamescopectl` subcommands — a client wanting them (the Steam client is the primary real-world consumer) binds `gamescope_control` directly and issues the Wayland request itself, using the info dump / feature-support path above as a reference for the wire format.
